## Context

The idea-window demo at `registry/demo/components/idea-window/index.tsx` currently uses `buildProjectData()` — a ~800-line function that manually creates ~90 tree nodes with hardcoded paths. The center panel has a static HTML mock of a code editor. The demo was recently updated to integrate the real `CodeEditor` component, but the tree data is still fake and disconnected from the editor.

The project has a build-time registry build script at `apps/www/scripts/build-registry.mts` that already runs as part of `pnpm registry:build`. Adding another build-time script fits the existing pattern.

## Goals / Non-Goals

**Goals:**
- Build-time script scans real project directory, outputs TypeScript module with tree structure + file contents
- Demo shows real project file tree in left panel via `DynamicTree`
- Clicking a file in the tree opens it in Ace Editor (in-memory)
- Multiple files open simultaneously with tab switching
- Modified/dirty indicator on tabs (`●` dot)
- Bottom panel shows chronological operation log (open, close, modify, tab-switch)
- Tree add/delete operate on in-memory data only, no real filesystem changes
- Remove right panel (Debug) and simplify the demo layout

**Non-Goals:**
- File system write-back (editing is in-memory only)
- Build-time script watching for file changes (manual re-run required)
- Syntax highlighting for all 120+ Ace modes (only common web project modes)
- File search or filtering in the tree
- Drag-and-drop in the tree

## Decisions

### 1. Build-time script generates static TypeScript module

**Decision**: Create `apps/www/scripts/generate-project-data.ts` that runs at build time, scans the project directory, and outputs `apps/www/registry/demo/components/idea-window/project-data.ts`.

**Rationale**: The demo runs in the browser and cannot read the filesystem. A build-time script is the cleanest way to embed real project data. The generated module is a plain TypeScript file with exported typed data structures, imported directly by the demo component.

**Generated output structure:**
```ts
// Auto-generated by generate-project-data.ts — DO NOT EDIT
export interface TreeNode {
  id: string;           // relative path from project root
  label: string;        // filename or directory name
  isFolder: boolean;
  children?: string[];  // child IDs
}

export interface FileEntry {
  path: string;         // relative path
  mode: string;         // Ace mode (typescript, css, json, etc.)
  content: string;      // file content
}

export const treeNodes: Record<string, TreeNode>;
export const fileContents: Record<string, FileEntry>;
export const rootId: string;
```

### 2. Directory exclusion rules

**Decision**: The script excludes these directories/patterns:

| Pattern | Reason |
|---------|--------|
| `node_modules/` | Third-party deps, huge |
| `.next/` | Build artifacts |
| `.git/` | VCS data |
| `__registry__/` | Generated registry index |
| `.pnpm-store/` | Package manager cache |
| `.turbo/` | Turborepo cache |
| `.source/` | Generated source config |
| `.claude/`, `.cursor/` | IDE/CLI config |
| `openspec/.cache/` | OpenSpec cache |
| `*.log`, `*.tsbuildinfo` | Build artifacts |
| Files > 100KB | Performance guard |

**Rationale**: These are build artifacts, caches, or large generated files that would bloat the demo data without adding value.

### 3. File extension → Ace mode mapping

**Decision**: Simple lookup table for common web project file types:

```
.ts, .tsx → 'typescript'
.js, .mjs, .cjs → 'javascript'
.css → 'css'
.json → 'json'
.md, .mdx → 'markdown'
.html → 'html'
.yaml, .yml → 'yaml'
.sh, .bash → 'sh'
.xml → 'xml'
default → 'text'
```

**Rationale**: Covers 99% of files in this project. Unknown extensions fall back to plain text mode.

### 4. Demo state management — single component state

**Decision**: All demo state lives in the `IdeaWindowDemo` component using React `useState`.

```
State:
  openFiles: Map<string, {          // key = file path
    content: string,                 // current (possibly edited) content
    originalContent: string,         // original content for modified check
    mode: string,                    // Ace mode
  }>
  activeFile: string | null          // currently visible file path
  logs: Array<{                      // operation log entries
    time: string,                    // HH:mm:ss format
    action: 'open' | 'close' | 'modify' | 'switch',
    path: string,                    // file path
  }>
  treeData: { items, children }      // mutable copy of tree data for add/delete
```

**Rationale**: The demo is self-contained. No external state management needed. All state flows down to sub-components via props.

### 5. Tree → Editor interaction flow

```
User clicks tree item (file)
  → addLog('open', path)
  → If file not in openFiles: load from fileContents, add to openFiles
  → set activeFile = path
  → Editor shows file content

User types in editor (onChange)
  → If content !== originalContent:
       set modified = true for this file
       addLog('modify', path) (only on first modification)

User clicks tab close (×)
  → Remove file from openFiles
  → addLog('close', path)
  → If closed file was active: switch to next open tab or null

User clicks another tab
  → set activeFile = clicked tab id
  → addLog('switch', path)
```

### 6. Bottom panel as operation log

**Decision**: The `IdeaBottomPanel` shows a scrollable list of timestamped log entries.

**Format**: `[HH:mm:ss] Action: relative/path/to/file`

**Actions:**
- `Opened` — file opened from tree or tab
- `Modified` — file content changed (logged once per open session)
- `Closed` — tab closed
- `Switched to` — tab switched

**Rationale**: This demonstrates real-time state tracking and provides a visual debug trail of user interactions.

### 7. Layout: 2-panel + bottom

**Decision**: Remove the right panel (Debug). Use a 2-panel layout:

```
┌───────────────────────────────────────────┐
│ IdeaTopBar (File, Edit, View...)          │
├───┬───────────────────────────────────────┤
│   │                                       │
│ L │  Center: CodeEditor                   │
│ e │  ┌─────────────────────────────────┐  │
│ f │  │ CodeEditorTabs                  │  │
│ t │  ├─────────────────────────────────┤  │
│   │  │ CodeEditorPane (Ace)            │  │
│ B │  ├─────────────────────────────────┤  │
│ a │  │ CodeEditorStatusBar             │  │
│ r │  └─────────────────────────────────┘  │
│   │                                       │
├───┴───────────────────────────────────────┤
│ IdeaBottomPanel: Operation Log            │
├───────────────────────────────────────────┤
│ IdeaBottomBar                             │
└───────────────────────────────────────────┘
```

**Rationale**: Removing the right panel simplifies the demo and focuses attention on the tree-editor-log interaction which is the core feature.

### 8. Build integration

**Decision**: Add `generate-project-data` as a step in `pnpm registry:build`, running BEFORE the registry build script (since the generated file is imported by the demo).

**Rationale**: The generated `project-data.ts` must exist before the registry build script processes the demo component. Running it as a pre-step ensures the file is always up-to-date.

## Risks / Trade-offs

- **[Generated file size]** → The project has many files. Script includes size limits (100KB per file) to prevent bloating. Estimated total: ~200-400KB for the generated module.
- **[Stale data]** → Generated data is a snapshot. If files change, the script must be re-run. Mitigated by running as part of `pnpm registry:build`.
- **[Build time]** → File scanning adds ~1-2s to build. Acceptable.
- **[Tree depth]** → Deeply nested projects produce many tree nodes. Script should handle this gracefully with lazy loading via `DynamicTree`'s async feature.
